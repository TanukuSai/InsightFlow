1. Goals, scope, and assumptions
1.1 Product goal
InsightFlow ingests customer feedback from permitted sources, normalizes it into a canonical model, analyzes 
the text, groups recurring complaints into traceable issues, and presents filterable metrics and reports to 
authorized users.
1.2 In-scope capabilities
 CSV import with validation, row-level errors, deduplication, and asynchronous progress reporting.
 Authenticated webhooks with payload verification and replay/idempotency protection.
 Source-specific native API adapters with pagination, cursors, rate-limit handling, and deletion/update 
synchronization where the source supports it.
 AI-assisted sentiment, taxonomy assignment, topic extraction, and evidence-backed issue summaries.
 Dashboard metrics, category/trend views, a paginated feedback grid, issue lifecycle management, and 
asynchronous exports for large results.
 Tenant-aware access control, auditability, privacy controls, and monitoring suitable for an MVP.
1.3 Explicit non-goals for the MVP
 Universal scraping of arbitrary websites or guaranteed access to sources that block or restrict automated 
collection.
 A large microservices deployment, Kafka, Kubernetes, or a separate analytics warehouse before workload 
evidence requires them.
 Autonomous high-impact business actions. AI may recommend and summarize; users or deterministic 
policy approve critical actions.
 Claims of production scalability before representative workload and performance tests establish capacity.

2.2 Deployment boundary
Operate the Next.js app, FastAPI API, worker pools, Redis, and PostgreSQL as separate runtime units even if 
some are initially hosted on the same platform. Browser execution must be isolated from the API and database. 
The initial deployment can remain small: scale API and worker processes independently as measured demand 
grows.
3. Canonical data flow
3.1 CSV import
1. The client requests an import and uploads a file within a configurable size limit. FastAPI validates 
organization access, file type, request size, and import options.
2. The API writes an `ingest_jobs` record and an outbox event in one database transaction, then returns `202 
Accepted` with a `job_id`.
3. A dispatcher publishes the job to the Redis/Celery queue and marks the outbox event published. A reconciler 
re-dispatches durable pending jobs if publication was interrupted.
4. A worker streams/parses the file in bounded chunks, validates rows, records row-level failures, applies 
privacy controls, and upserts valid feedback records.
5. Analysis jobs are queued only for new or changed text (or when a re-analysis is explicitly requested). 
Progress and final counts are persisted in PostgreSQL.
3.2 Webhook ingestion
1. Receive only configured webhook routes; identify the source connection and owning organization from 
server-side configuration, not user-provided organization IDs in the payload.
2. Verify the signature against the raw request body, enforce a timestamp/replay window if supported by the 
provider, and validate the payload size and schema.
3. Persist a webhook receipt/event with an idempotency key before acknowledging successful receipt. 
Duplicate deliveries should return a safe acknowledgment without repeating side effects.
4. Normalize the event into the canonical record model and enqueue downstream work. Keep raw payload 
retention minimized and governed by the data-retention policy.
3.3 Native API collection
1. A user starts a source sync; the API checks permissions and connection health, creates a durable job, and 
returns immediately.
2. The adapter fetches data page-by-page using provider cursors, respects rate limits and retry headers, and 
checkpoints its next cursor only after the corresponding batch is durably committed.
3. Each record is normalized, deduplicated, compared for content changes, privacy-processed, and inserted or 
updated transactionally.

4. Source-supported edits and deletions are reconciled according to the connector policy and applicable source 
requirements. Unsupported deletion semantics must be documented, not silently ignored.
3.4 Browser-assisted extraction
Restricted fallback only
Browser automation is for explicitly approved source/domain adapters where authorized data access is available 
and a native API is not adequate. Do not design the product around bypassing bot defenses, login controls, 
paywalls, CAPTCHAs, or source restrictions.
 Run each browser task in a disposable isolated execution environment with no database credentials and 
minimal secrets.
 Restrict outbound traffic using an enforceable egress policy; validate URL schemes, DNS resolutions, 
redirect destinations, and block loopback, private, link-local, and metadata-service destinations. URL-string 
validation alone is not enough [R5].
 Set hard page count, execution time, memory, download, and navigation limits. Close contexts and remove 
temporary artifacts after each job.
 Prefer source-specific selectors and parsers. Use an LLM only when necessary to interpret retrieved 
content; validate extracted records against a strict schema.
 Treat page content as untrusted data and possible prompt injection. Extraction models receive no tools or 
credentials and cannot issue application actions.
3.5 AI analysis and issue aggregation
1. Send only the minimum required, privacy-processed text and metadata to the configured analysis provider.
2. Validate the response against a versioned schema. Invalid, incomplete, or out-of-range values are retried 
only when the error is plausibly transient; persistent schema failures become explicit failed analysis 
records.
3. Persist each analysis version with provider/model, prompt version, taxonomy version, status, timestamps, 
and distinct sentiment/confidence fields.
4. Run a separate issue-aggregation step to link related feedback, update counts and time windows, generate 
evidence-backed summaries, and apply explicit priority policy.
5. Critical findings should be reviewable and traceable to supporting feedback. AI-generated recommendations 
must not be represented as confirmed facts.

4.1 Identifier and deduplication rules
 Generate an internal `feedback_id` UUID for every record. Never use a third-party ID as the primary key for 
the internal data model.
 Preserve the source-provided identifier separately as `source_external_id`.
 For non-null external IDs, enforce uniqueness on the appropriate source scope (recommended: 
`organization_id + connection_id + source_external_id`). Use a database unique constraint or partial unique 
index, not an application-only pre-check [R6].
 For CSV rows without a stable external ID, use a documented import-scoped idempotency/deduplication 
rule. A text hash can assist but should not be the only global identity rule; identical feedback can 
legitimately occur more than once.
 Use transactions for feedback upsert plus analysis scheduling metadata. Repeated job execution must not 
create duplicate feedback, analysis-current pointers, or issue links.

4.3 Integrity, indexes, and access rules
 Every tenant-owned table must include `organization_id` directly or be reachable through a constrained, 
validated relationship to a tenant-owned parent.
 Add foreign keys and check constraints for valid statuses, priorities, ratings, score ranges, and relationship 
integrity.
 Recommended initial indexes: feedback by `(organization_id, source_created_at DESC)`, current analyses by 
feedback ID, analyses by `(organization_id, primary_category, sentiment_label)`, issues by `(organization_id, 
status, priority)`, jobs by `(organization_id, created_at DESC)`, and issue links by both foreign keys.
 Enable and test Row Level Security on any table exposed through the Supabase Data API; use least-
privilege grants and never expose service-role/secret keys to the browser [R2].
 If FastAPI uses privileged server credentials, every endpoint must still authorize the user and constrain 
every query by organization. Privileged credentials must remain server-only; add regression tests for 
cross-tenant access.

6. AI analysis architecture
6.1 Provider abstraction
Use an internal adapter boundary so the core domain model is not coupled to a particular model vendor. The 
exact interface can be implemented in Python; the minimum contract is that input/output schemas are 
versioned and provider failures map to stable application errors.
class AnalysisProvider(Protocol):
    async def analyze_batch(
        self,
        items: list[AnalysisInput],
        taxonomy: TaxonomyVersion,
    ) -> list[AnalysisResult]: ...
The provider adapter returns validated sentiment, category, topics, and optional structured explanation fields. 
It must also report provider/model identifiers and usage metadata where available. The application persists the 
results and owns all issue lifecycle and authorization decisions.
6.2 Adaption Labs integration gate
The original design assigns per-feedback classification and recommendations to Adaption Labs. Current public 
Adaption documentation describes Adaptive Data and AutoScientist, including data optimization and model-
training workflows [R1]. This does not prove that the exact real-time inference contract required here is 
available. Keep the integration provider-neutral until confirmed.

If Adaption cannot provide the required real-time inference, use a validated inference provider behind

verified data-optimization, dataset preparation, or model-training/evaluation workflow rather than pretending it 
is the production scoring API.

6.3 Output schema and quality controls
 Use strict JSON/schema validation and permitted enum values. Reject or mark invalid any result that 
cannot be parsed safely.
 Keep `sentiment_score` and `confidence_score` separate. Only persist confidence if the provider 
meaningfully defines it; model self-reported confidence is not automatically calibrated probability.
 Use a tenant-owned taxonomy version. If a category is outside the current taxonomy, map to 
`unknown`/`needs_review` rather than silently inventing a new category.
 Maintain a human-reviewed evaluation set and measure classification quality by source, language, 
category, and relevant demographic/locale slices when appropriate and lawful.
 Track prompt/config versions and model versions. Reprocessing is an explicit job with deduplication and 
an auditable version change.
 Do not allow model output to issue SQL, call arbitrary tools, alter permissions, or directly change issue 
status.
 Minimize text sent to external AI services; redact according to policy and record a provider request ID 
without logging sensitive prompt content.
6.4 Issue detection is a separate domain process
Individual feedback analysis and issue detection must remain separate. A single negative review is not, by 
itself, proof of a critical incident. The aggregation service should combine evidence such as frequency, recency, 
rating, category, and approved severity rules. AI may draft an explanation or recommendation, but the issue 
record must link to supporting feedback and expose its evidence count and last-seen time.
Priority Recommended control
Critical Only based on defined objective triggers or reviewer approval; 
always show supporting records and why the rule triggered.
High Evidence threshold or severity rule met; visibly flag 
uncertainty and allow rapid human review.
Medium Recurring or materially negative pattern that needs 
investigation.
Low Weak or early signal; track without overstating certainty.
7. Security, privacy, and source governance
7.1 Identity and tenant isolation
 Authenticate users using the chosen identity provider (Supabase Auth is the default candidate unless a 
project constraint dictates otherwise). Validate session/JWT claims server-side in FastAPI.
 Authorize every operation based on user, organization membership, role, object ownership, and state 
transition. Hiding UI controls is not authorization.
 Require tenant scoping on all reads and writes. Test cross-tenant reads, updates, exports, job access, and 
issue status changes as part of automated security tests.
 Use least-privilege database roles. Enable RLS on exposed Supabase tables and test policies. Never expose 
database passwords, AI keys, source credentials, or Supabase service-role/secret keys in the frontend [R2].

7.2 Webhook security
 Verify signatures on the exact raw request body using constant-time comparison where supported by the 
framework/library.
 Support timestamp validation and replay windows when the source signs timestamps; persist provider 
event IDs or idempotency keys.
 Enforce payload-size/time limits and reject unsupported content types. Do not log authentication headers 
or signing secrets.
 Rotate secrets and store them in managed environment secrets or a secret manager; keep secret references 
separate from ordinary connection configuration.
7.3 Privacy and retention
 Define which text is retained. Default to storing redacted text used for analysis; keep unredacted originals 
only if a documented business need, access restriction, retention limit, and deletion path exist.
 Regex can catch predictable patterns but is not a complete PII detector. Combine deterministic rules with 
additional detection appropriate to source and region; allow user review of redaction quality.
 Define deletion and correction workflows across feedback, analyses, issue links, cached aggregates, and 
exports. Apply source deletion requirements where contractually/legally applicable.
 Set retention periods for original payloads, redacted text, exports, job errors, and audit data. Avoid placing 
customer text or secrets in application logs.
 Review the privacy terms and retention practices of every external AI and source provider before sending 
data.
7.4 Safe browser execution and untrusted content
 Use a source/domain allowlist where possible. Restrict browser egress at the network layer and block 
loopback, private, link-local, multicast, and cloud metadata destinations.
 Resolve DNS and validate every redirect and destination before navigation and subsequent requests; use 
network-level enforcement to reduce DNS-rebinding and redirect bypass risk [R5].
 Use ephemeral browser contexts and containers; disable unnecessary downloads, permissions, extensions, 
and persistent profiles. Browser contexts provide session isolation but are not a substitute for OS/container 
and network isolation [R4].
 Treat retrieved page text as untrusted input. Prompt templates must delimit source content as data, and 
extraction models must have no application-action tools or secrets.
 Observe source terms, permissions, and provider API limits. The system must fail visibly when a source 
denies access rather than trying to circumvent the control.
7.5 Audit events
At minimum, audit login/security-relevant events through the identity provider, source connection 
creation/rotation, imports and exports, member/role changes, issue status or priority changes, and 
administrator overrides. Audit records should be append-only to ordinary application users, tenant-scoped, 
and retained according to policy.

8.3 Retry and idempotency policy
 Use Celery as the initial worker framework rather than leaving a Celery/RQ choice undecided. Configure 
retries by error class, exponential backoff and jitter for transient errors, and maximum attempts [R3].
 Do not retry permanent validation failures, revoked credentials, forbidden source access, or unsupported 
response schemas without intervention.
 Design tasks to be idempotent. Assume at-least-once execution/redelivery can occur; never claim exactly-
once processing. Celery documentation explicitly recommends idempotent task functions for safe 
redelivery [R3].
 Persist per-record outcomes so a retry processes failed/retryable items without repeating successful side 
effects.
 Add a reconciler that detects stale `queued`/`running` jobs, unpublished outbox events, and jobs with no 
heartbeat beyond a configured threshold.
 Define cancellation semantics: stop scheduling new items, allow safe in-flight work to finish or terminate, 
and record what has already been committed.

9. Performance, scaling, and observability
9.1 Scale by workload, not by fashion
Start with a modular deployment and separate processes for the API and each worker pool. Scale each 
independently using queue depth, processing latency, and resource utilization. Do not add Kafka, Kubernetes, a 
data warehouse, or additional microservices until load tests or operational limits justify them.
9.2 Performance controls
 Use bounded batches for CSV parsing, database upserts, and AI inference. Avoid placing tens of thousands 
of individual tasks into Redis from a single synchronous request.
 Use connection pooling and database indexes for common organization-scoped filters and chronological 
queries.
 Use cursor-based pagination and server-side filter limits. Never fetch all feedback to the browser for 
filtering.
 Measure dashboard query plans before adding caching or materialized aggregates. If query cost grows, 
introduce precomputed tenant-scoped daily aggregates with a defined freshness SLA.
 Generate large exports asynchronously. Avoid holding a database transaction open while a file is 
downloaded.
 Configure per-provider request/concurrency budgets and global job fairness so one tenant cannot 
monopolize workers.
