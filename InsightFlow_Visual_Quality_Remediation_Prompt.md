## 2. Product vision and visual signature

InsightFlow is an evidence-driven customer-feedback intelligence product. Its distinctive visual signature is a living field of dots: scattered customer noise becomes repeated patterns, then meaningful groups, then connected evidence and decisions.

The product should feel like a carefully art-directed, premium analytics application—not a generic admin template, not a standard shadcn dashboard, and not a collection of cards generated by an AI boilerplate tool.

The visual direction must combine:

- A distinctive particle/dot language used intentionally.
- Refined light-first glassmorphism.
- A richer, more characterful color system.
- Clear typographic hierarchy and calm whitespace.
- High-quality, legible and truthful data visualization.
- Subtle, purposeful motion with reduced-motion alternatives.
- Stable, precise, evidence-led enterprise interaction patterns.

Avoid generic purple AI gradients, neon decoration, giant blurred blobs, rainbow color palettes, random floating cards, excessive rounded boxes, glass on every surface, identical charts in card containers, gratuitous animation, or icon decoration without meaning.

Do not confuse visual sophistication with adding more effects. Every visual treatment must improve orientation, comprehension, focus, or product identity.

Refine it into a layered system that keeps the product light and calm but adds deeper contrast, richer accents, and a memorable signature. Keep the original porcelain/forest/sage intent, but do not use the same green for every positive, selected, chart, and interactive state.

Use this as a coherent starting proposal; inspect it in context and refine accessible contrast rather than treating the hex values as untouchable:

- Warm porcelain canvas: `#F6F5F0`
- Clean white: `#FFFFFF`
- Soft stone surface: `#EEEFE8`
- Raised white surface: `rgba(255,255,255,0.82)`
- Glass edge: `rgba(255,255,255,0.78)`
- Subtle separator: `#DDE2DA`

### Text and deep contrast
- Main ink: `#172522`
- Secondary ink: `#44544F`
- Muted ink: `#65736D`
- Deep pine: `#123D35`

### Brand and interaction
- Forest: `#21624E`
- Emerald: `#2C8064`
- Signature soft mint: `#A8E8C9`
- Pale mint wash: `#E1F4E9`
- Focus/selection ring: a high-contrast forest/teal treatment with a visible outline, not color alone

### Data-series and semantic accents
- Blue: `#5877B7`
- Terracotta/coral: `#C8614D`
- Amber: `#C48A2B`
- Plum/brown neutral: `#8A7187` only for an explicitly justified neutral category, not as a generic AI accent
- Positive: forest/emerald

Do not rely on the sample colors blindly. Check contrast, especially small labels and chart marks. Use semantic color consistently. Positive sentiment must not be conflated with the source category. - Page background and surfaces.
- Text levels.

- Border colors.
- Glass levels.
- Shadow/elevation levels.
- Radius sizes.
- Spacing and type scale where the existing system supports them.

Keep marketing visuals more expressive than data-dense workspace surfaces, but make both clearly the same brand.

## 4. Glassmorphism: visible, tasteful, readable

Implement real glass treatments in the actual React/CSS components. The effect should be apparent, not merely documented.

Use glass selectively for:

- Floating marketing navigation.
- Application header and selected floating controls.
- Select KPI surfaces where there is enough contrast behind the card.
- AI layout recommendation/preview panels.
- Contextual menus, popovers, filter panels, selected drawers, and notification toasts.
- The particle field's overlay controls.

Implement reusable surface variants such as `glass-subtle`, `glass-raised`, and `glass-overlay`. Adapt the names to existing conventions instead of duplicating styles.

Suggested starting ranges:
- Subtle glass: white at 75–88% opacity, 10–16px backdrop blur.
- Raised glass: white at 62–78% opacity, 16–24px blur, soft border and restrained shadow.
- Overlay glass: white at 84–94% opacity for legibility above dense content.

Use `backdrop-filter` and `-webkit-backdrop-filter` with a legible fallback for unsupported browsers. Include a subtle edge highlight, controlled shadow, and meaningful layer hierarchy. Test against actual page backgrounds; opacity values must be adjusted to achieve contrast.

Do **not** apply glass to every chart plot area, every table, or every feedback row. Tables, import previews, source excerpts, forms, and dense chart labels should use opaque or nearly opaque surfaces. A few distinct glass layers over clean content will look more expensive than making every box translucent.

## 5. Make the dot field the signature—not a distracting screensaver

Inspect the current `DataFieldCanvas.tsx` and `index.html` reference before modifying. Preserve the metaphor of scattered feedback becoming patterns and evidence, but improve visual clarity, pacing, and visual finish.

### Public landing page

- Use a strong editorial split: confident headline and concise copy on one side; a substantial open particle field on the other.
- The particle field should have depth, scale variation, restrained soft glow, and a considered composition.
- Dots should feel like meaningful data points, not random confetti or a starfield.
- Movement should be slow, smooth, and choreographed, with occasional connection lines when nodes form patterns.
- Let the field transition through the four conceptual stages: Scattered → Repeated patterns → Category groups → Evidence connections.
- Show the stage changes only in a purposeful story interaction or a controlled automatic sequence that does not compete with reading.
- Never claim that decorative particles correspond to live database rows unless the visualization really is bound to those rows.
- Keep headings and CTAs clear; particles must never lower text contrast.

### In-product use

- Make the dot field more restrained inside the authenticated analytics workspace.
- Never place an animated particle layer underneath a dense data table or interfere with chart reading.
- Prefer a compact decorative/interactive motif in an insight empty state, analysis-in-progress panel, or landing-level product story.
- If a visualization represents real data, make the connection explicit and derive it from actual API results.

### Technical quality

- Preserve or improve device pixel ratio capping, offscreen pausing, and `prefers-reduced-motion` support.
- Avoid a permanent animation loop when the page is hidden or offscreen.
- Support resize and high-DPI displays correctly.
- Ensure canvas is decorative to screen readers unless there is a meaningful textual alternative.
- Avoid expensive per-frame React state updates; use canvas rendering appropriately.
- Never let the dot field block clicks or keyboard access.

## 6. Motion system: intentional, polished, coherent

The present motion language needs to feel designed rather than incidental. Establish shared motion tokens and use them consistently. Use the project's existing animation library where possible; do not add a large dependency for tiny transitions. If adding Motion for React is genuinely useful, check compatibility and justify the dependency.

### Motion principles

1. Motion explains hierarchy, cause and effect, or state change.
2. Interactive feedback is immediate.
3. Data visualization animation must not delay interpretation.
4. No element should jiggle, float, pulse, or shimmer indefinitely without a functional reason.
5. Do not animate every card on initial render; create a clear focal sequence.
6. Preserve layout stability. Avoid large layout shifts or moving a card while the user is interacting with it.
7. Respect `prefers-reduced-motion: reduce` throughout the product.

### Timing guidelines

- Button hover/press: 100–180ms.
- Small color, border, and focus transitions: 120–200ms.
- Dropdown/popover: 160–220ms.
- Drawer/dialog: 200–280ms.
- KPI 3D flip: 350–450ms.
- Dashboard layout transitions: 250–350ms.
- Page-level content introduction: a restrained 180–300ms sequence, only where useful.
- Chart reveal: generally 350–650ms, once, after valid data arrives; skip or shorten for updates and reduced motion.

### Dashboard cards

- Hover: subtle elevation and border/light response; avoid exaggerated translation.
- Focus: clear accessible outline, not hover-only feedback.
- KPI flip: true 3D front/back using CSS transforms, stable footprint, clear toggle/return affordance, proper button semantics, and no important action hidden solely on the back.
- Avoid hover-triggered flips; use explicit click/keyboard activation so users control the card.

### Filters, drawers, and dialogs

- A drawer should enter/exit from a clear direction and settle quickly.
- A popover should appear anchored to the control that opened it.
- Focus must move appropriately into dialogs and return to the trigger when closed in the actual implementation.
- Escape closes dismissible overlays.
- Backdrop dismissal must not accidentally lose unsaved work without warning.

### Loading and analysis

- Use stable skeletons or a meaningful progress state, not endless shimmer.
- Poll real job status where the backend supports it.
- Do not advance fake percentages or claim stages the worker cannot report.
- On completion, reveal valid results smoothly without moving chart axes or changing the interpretation unexpectedly.

## 7. Data visualization: redesign to professional analytics standards

The charts must be among the strongest parts of the product. Audit every current visualization and redesign it for readability, truthful encoding, hierarchy, and interaction. Do not add more charts just to make the dashboard look busy.

Use the chart library already installed in the repository. If Recharts is used, build reusable chart wrappers and tooltip/legend patterns around it. Do not introduce a second charting library without a clear technical reason.

### General chart rules

- Every chart must have a question it answers.
- Give it a precise title and, when useful, a short explanatory subtitle.
- Use a consistent plotting grid, axis type, label style, and tooltip format.
- Keep gridlines light and restrained.
- Avoid 3D charts, misleading perspective, decorative donut charts with no analytical purpose, and gradient fills that obscure magnitude.
- Use direct labels where practical.
- Always show units and sample sizes when they matter.
- Format large counts consistently (e.g. `7,000`).
- Ensure chart labels don't collide at common viewport widths.
- Design no-data, loading, error, and partial-data states for every chart.
- Tooltips must show exact values and the meaning of the measure.
- Legends must be understandable and, when filters are interactive, show a selected state.
- Use accessible text descriptions or a textual summary for important chart findings.
- Don't rely on color alone; pair colors with labels, markers, patterns, or direct annotations where feasible.
- Charts must resize correctly on desktop, tablet, and mobile.
- Avoid animation on every re-render. Animate the first valid reveal only, and use reduced-motion behavior.

### Required dashboard visualizations

#### A. Source category distribution

The dataset's original fields are `review` and `category`. Show the source categories and their row counts and percentages using a polished horizontal bar chart or ranked bar list. This is a good fit because category labels are long and category counts are comparable.

- Sort consistently, preferably descending by count.
- Display each category's row count and share.
- Label it as source category distribution, not sentiment.
- Include the total row count and the calculation denominator.
- Make category bars clickable only if the UI can apply the corresponding real feedback filter.
- Use category colors consistently but do not map the categories to positive/negative sentiment colors.

#### B. Sentiment distribution

Display only after sentiment has actually been computed and returned by the backend.

- Use an accessible stacked horizontal bar or a restrained donut only if category comparison is not the main task.
- Show counts and percentages for positive, neutral, negative, and unknown/unclassified.
- Keep `unknown` distinct; never silently omit unclassified rows from the chart's total without explaining the denominator.
- If sentiment is not analyzed, show a purposeful state explaining that the model output is required and a real action to start analysis if that endpoint exists.
- Never render demo sentiment values as if they belong to the uploaded dataset.

#### C. Recurring statements / repeated text

The supplied CSV has many repeated strings. The known baseline is approximately 7,000 rows and 320 unique exact review strings, but recalculate from the current data rather than hardcode those numbers.

- Distinguish total rows, unique exact statements, and additional repeat rows.
- Use a ranked horizontal bar chart or Pareto-style view for top repeated statements only if the backend provides real statement groups and counts.
- Truncate labels safely and reveal the full verbatim text in a tooltip or detail panel.
- Explicitly state that repeated rows are not proof of distinct affected customers or issue severity.
- Do not label exact duplicate groups as semantic clusters unless semantic grouping has actually been performed.
- If the backend returns a semantic cluster count, explain its method and avoid mixing it with exact-text deduplication.

#### D. Priority issues

Use an evidence-oriented ranked list rather than a chart with an unexplained priority score.

Each item must show:
- Issue title.
- Priority and status.
- A concise reason for its rank.
- Supporting record count, if available.
- Unique statement count, if available.
- Access to verbatim evidence.
- A useful next action.

Never show a red `Critical` label merely because an exact statement repeats many times. Severity should come from a defensible backend field/rule and the UI must explain why it was assigned. If priority is proposed and unverified, label it as proposed and needing review.

#### E. Temporal trend

The actual source schema may lack timestamps. Inspect the database and current API.

- If there are no verified source timestamps, DO NOT draw a real historical trend line and do not fabricate weeks, percentages, dates, or period-over-period changes.
- Replace the trend area with a useful supported view: category distribution, repeat-frequency distribution, analysis coverage, or an explicit temporal-data-unavailable explanation.
- If some valid timestamps exist, use only those records, disclose the coverage, and never imply that untimestamped rows are in the timeline.
- If the app has a clearly labeled simulated demo dataset, keep its trends isolated from the actual uploaded dataset and visibly mark it as illustrative.

### Dashboard composition

Create an intentional hierarchy, not a uniform wall of cards:

1. Page title, dataset context, and principal actions.
2. Three or fewer high-value KPI cards with definitions and data provenance.
3. One primary analysis visualization that is genuinely supported by the data.
4. Priority issues/evidence, prominently placed.
5. Supporting source-category/repeat distribution and recent feedback.
6. Limitations and data-quality context placed clearly but unobtrusively.

Avoid multiple competing primary charts. Use asymmetrical layout if it improves hierarchy, but maintain a stable grid and responsive rules.

### Metric cards

Each metric must have:
- A meaningful label.
- A truthful value.
- A short explanation or contextual subtitle.
- A unit or denominator where necessary.
- A path to details, where implemented.

Do not show percentages as comparisons to a previous period unless valid prior-period data exists. Do not turn missing metrics into zero. Use `Not analyzed`, `Unavailable`, or an explicit reason as appropriate.

## 8. Make the interface data-driven, not mock-data-driven

Use the existing typed API client and actual FastAPI endpoints. The current project report identifies the backend base URL as `http://127.0.0.1:8001` and lists routes for health, datasets, dashboard metrics, feedback, issues, recommendations, imports, and reports. Verify the actual OpenAPI schema and current implementation before relying on those paths.

Requirements:

- A single configured API base URL; do not duplicate localhost URLs across components.
- Typed request and response contracts aligned with the actual API.
- Centralized error parsing and consistent loading/empty/error states.
- Abort stale search requests and debounce search input where appropriate.
- Use server pagination rather than loading all 7,000 records into the browser.
- Preserve backend values and explicit unknown/null states.
- Derive charts from API results, not hardcoded arrays.
- When an action fails, show the error and retry/recovery option rather than updating the UI as if it succeeded.
- After import, refresh dataset and dashboard queries from the backend.
- After analysis, refresh only after the job reaches a real completed state.
- After issue status changes, update the UI from the actual mutation response or safely re-fetch.
- Report exports must download the actual backend-generated file/response.
- Distinguish source data from inferred analysis in types, labels, and UI copy.

If you need demo data for a visual regression route, keep it explicitly isolated from the operational workspace. Never silently fall back from a failed backend call to fake metrics.

## 9. UI states, accessibility, and responsiveness

For every important route and major card/chart, audit:

- Initial loading.
- Empty/unconfigured state.
- Successful populated state.
- Partial data.
- API failure.
- Retry.
- Filtered/no-results state.
- Disabled/pending interaction.

Accessibility requirements:

- Visible keyboard focus.
- Correct button/link semantics.
- Keyboard-usable KPI flip, menus, filters, drawers, and chart controls.
- Reduced-motion support.
- Textual context for chart takeaways.
- Sufficient foreground/background contrast across glass surfaces.
- No status conveyed by color alone.
- Mobile controls large enough to use comfortably.

Responsive breakpoints must intentionally adapt layouts rather than simply scale them down. Check at least 1440px, 1024px, 768px, and 390px widths. The particle canvas must resize without blur or horizontal overflow. Mobile charts must retain readable labels and not force the entire page to scroll horizontally.

## 13. Acceptance criteria

The work is not done until all of the following are true:

### Visual identity
- The color palette is richer and more distinctive while preserving the light-first product intent.
- Selected surfaces have visible, believable glassmorphism.
- Dense information remains readable.
- The dot field is a recognizable InsightFlow signature, not generic background decoration.
- Pages have a coherent design system and clear visual hierarchy.
- The result does not resemble a default AI-generated admin template.

### Motion
- Animations are deliberate and consistent.
- No unnecessary permanent motion or excessive shimmer exists.
- KPI flips and overlays work via keyboard as well as pointer.
- Reduced motion is supported.
- Motion does not obscure or delay data interpretation.

### Data visualization
- Charts answer specific questions and use appropriate encodings.
- All values are derived from backend responses.
- Source category is distinct from sentiment.
- Unknown/unclassified records are represented honestly.
- No fabricated trends or period comparisons are shown.
- Duplicate counts are not described as distinct customers or severity.
- Charts have good labels, legends/tooltips, responsive sizing, and empty/error states.
- Priority issues expose evidence and rationale.

### Integration and stability
- Existing routes and core workflows still work.
- API errors are not hidden by fabricated fallback content.
- Search/filtering is properly bounded and responsive.
- Import, issue updates, and report exports remain functional.
- Lint, type checking, and production build pass.
- Existing backend tests pass.
- Browser screenshots confirm the improvement on desktop and mobile.
